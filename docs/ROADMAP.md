DPDP-oriented account basics now include legal-review placeholder pages, explicit versioned signup and emergency-sharing consent records, revocation of active emergency links when that consent is withdrawn, and a minimal owner-only audit viewer. These are implementation controls only; the placeholder legal text requires legal review and this does not establish DPDP compliance.

The web UI has a cookie-backed English/Hindi dictionary for the requested account navigation, authentication, document review, timeline, emergency, wallet card, and privacy pages. Offline extraction recognizes common transliterated labels (`naam`, `umra`/`umar`, `dawa`, `jaanch`, `nidaan`). Hindi-script OCR is not available in the installed RapidOCR model/configuration; multilingual OCR remains open.

FHIR export is available from Data & privacy as a FHIR R4-aligned Bundle containing the patient profile and supported patient-confirmed timeline entries (allergies, diagnoses, medications, labs/observations, and procedures). Entries with unresolved conflicts or uncertainty are excluded, and timeline/document provenance is carried in metadata extensions. This export is not an ABDM/NHCX profile implementation or conformance claim; it does not embed document files.

The app now publishes an installable web manifest and a service worker that caches only its fixed static offline-card shell (HTML, CSS, scripts, manifest, and icon). API requests, public emergency routes, documents, and Next.js pages are never added to the service-worker cache. Patients can opt in to save selected profile fields in IndexedDB, encrypted with an AES-GCM key derived from an 8+ digit PIN using PBKDF2; the standalone bilingual page unlocks the card offline and shows its last-sync time. Desktop Chromium E2E covers encrypted storage, rejection of a wrong PIN, offline unlock, and removal. Android/iOS home-screen installation was not manually exercised on physical devices.

Local OCR, rule extraction, source-linked review, timeline filters/editing/deletion, emergency QR, expiry/revocation/renewal, field selection, access history, family document permissions, dependent archival, account export/deletion, email verification/reset, rate-limit failure modes, malware scanning, and encryption rotation have automated coverage. The single browser journey covers signup consents, persistent English/Hindi switching, default no-AI consent visibility, extraction review/confirmation, timeline, QR access from another browser, access history, renewal/revocation, family switching/isolation, FHIR/account downloads, emergency-consent withdrawal, and deletion. Targeted axe checks and keyboard/mobile assertions run in Chromium. Live email delivery, AI-provider behavior, PostgreSQL service execution, and Docker images have not been verified against deployed services in this environment. The ABHA/ABDM sandbox application is pending; the connector remains disabled pending official docs, credentials, approvals, and verified API workflows. The user-provided dependent-authority checkbox is an attestation and does not establish legal authority. Pilot operation still requires Docker/Compose validation, restore testing, external security review, and legal/privacy review.

The dashboard includes a four-step first-run checklist for profile details, uploading a record, confirming a reviewed fact, and creating an emergency link. Targeted English-language Chromium axe checks cover login, signup, document review, the account emergency page, the public scan page, and Data & privacy; keyboard flow covers auth forms and the document sheet focus trap, Escape close, and focus restoration. Mobile width is checked across the primary routes. These checks do not replace manual assistive-technology or real-device testing.

## Local presentation demo

The local demo is implemented and verified. It uses the existing services and a reserved, pre-seeded fictional patient; login sets the standard HttpOnly cookie. Five private synthetic PDF fixtures, patient-reported details, a dependent, source-linked timeline facts, pending simulated extraction, consent/audit entries, and an active emergency share are created idempotently. Profile updates, uploads/previews, candidate review, timeline persistence, QR creation/public access/revocation, family switching, privacy history, FHIR download, and English/Hindi preference use the existing APIs. No external email or AI credentials are required. See `docs/DEMO_IMPLEMENTATION_REPORT.md` for exact checks, data-preservation evidence, and remaining limits.

The demo is a local presentation aid, not a clinical dataset or production authentication mode. Live OCR success on the generated demo PDFs, phone scanning over a real LAN, physical-device accessibility, and live ABHA/ABDM exchange were not verified in this run. The external ABDM sandbox workflow remains blocked pending official access and credentials.
